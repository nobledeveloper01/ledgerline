# ADR-0005 — An ORM's schema file is read as text, and never run

**Status.** Accepted, 2026-09-23. Phase 5.

## Context

Two large populations have no SQL in the repository at all.

A Rails team has `db/schema.rb`: Ruby, generated by Rails from the database
itself, checked in, and for that team the authoritative statement of what
exists. A Django team has `models.py` per app: Python, from which the tables
are derived by convention, with migrations that are also Python.

Both files are *programs*. The obvious way to read them is to run them — load
`schema.rb` in a Ruby process with a recording connection, or import
`models.py` and ask Django's `_meta`. That is what every tool in the category
does, and it is what makes those tools require a working application
environment to draw a picture.

## Decision

**Neither file is ever executed. Both are read as text.**

`parseRailsSchema` reads `create_table`, `t.<type>`, `t.references`,
`t.timestamps`, `t.index … unique: true`, and `add_foreign_key`.
`parseDjangoModels` reads `class X(models.Model)`, the field classes, `Meta`'s
`db_table`, `unique_together`, `managed` and `abstract`, and the three relation
fields.

Three consequences, all accepted deliberately:

1. **Conventions have to be reproduced, and reproduced visibly.** Django's
   table name is `<app label>_<model lowercased>`, and the app label is the
   directory. So the reader takes the *path*, not just the text. Rails derives
   a foreign key's column by singularising the table name, so this repository
   contains an inflector — a small one, with the regular rules and a list of
   irregulars.
2. **What the convention cannot reach is reported, never guessed.** If
   `add_foreign_key "traps", "mice"` implies a column `traps.mouse_id` and the
   table has no such column, no edge is drawn and the line is listed as unread.
   A `ForeignKey('auth.User')` in a file that defines no `User` is listed the
   same way. An invented edge is worse than a missing one, because the diagram
   would look complete — which is rule 2 of this repository applied to a
   reader instead of to a query.
3. **A `ManyToManyField` becomes a table**, because Django creates one. A
   diagram that omits the join table is missing a table that exists.

The readers are ordered behind migrations, never beside them: migrations when
a repository has them, the ORM file when it does not. Two answers to one
question is the thing this tool exists to complain about, not to produce.

## Consequences

The reader is a grammar's worth of regular expressions, and it will meet a
`schema.rb` it does not fully understand. That is why every reader returns
`unread` alongside the schema — a list of lines with line numbers — rather
than a schema alone. A user can see the size of what was skipped; a silent
reader cannot be audited.

Running the file would be more complete and would cost a Ruby toolchain, a
Python toolchain, a working settings module, and arbitrary code execution on
whatever runs `ledgerline`. Nothing leaves this machine (rule 4), and that
includes control of it.

## Alternatives rejected

- **Shell out to `rails runner` / `django-admin inspectdb`.** Complete, and
  requires the application to boot. A diagram tool that needs your app's
  environment is the tool teams already have and do not run.
- **Read the ORM's migrations instead.** Rails and Django migrations are
  programs too, and are worse: they are a sequence of programs, each of which
  may branch on the database's state.
- **Read nothing and tell Rails and Django users to export SQL.** Honest, and
  it hands the two biggest populations of "no SQL in the repository" nothing.
