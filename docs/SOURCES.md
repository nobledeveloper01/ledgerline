# Where a schema comes from

Ten sources. **Nine of them are files, and not one of those nine is ever
executed** — no Ruby process, no Python import, no `tsc`, no .NET SDK, no
`rails runner`. The tenth is a live database, read-only, and only when you
hand the tool a URL.

That rule is [ADR-0005](adr/0005-an-orm-file-is-read-as-text-and-never-run.md):
running a repository's code to draw its diagram is a liability, not a feature.
It is also why this tool works on a laptop with nothing installed, on a
repository whose application will not boot.

Every reader returns the schema **and a list of what it did not read** — lines
with line numbers. A silent reader cannot be audited, and every one of these
meets something it does not understand.

---

## The rule they all share

**Where a convention cannot be reproduced, the line is reported and no edge is
drawn.**

Rails derives a foreign key's column by singularising a table name, so this
repository contains an inflector, so there are plurals it will get wrong.
When `add_foreign_key "traps", "mice"` implies a column `traps.mouse_id` and
the table has no such column, nothing is drawn and the line is listed as
unread.

An invented edge is worse than a missing one, because the diagram would look
complete.

---

## 1. SQL migrations

Directories of `.sql`, applied in name order, which is every migration tool's
own convention. `*.down.sql` and anything under `down/` is skipped: folding an
undo into the schema would drop what the up script created.

Reads `CREATE TABLE`, `ALTER TABLE` in its many forms, `DROP`, `RENAME`,
`CREATE UNIQUE INDEX`, and the constraint syntax in all its spellings. Folds
200 real migration files into one schema and comes out byte-identical to what
a live PostgreSQL 16 reports — that is the Phase 1 gate, and it is a test that
runs when a database is available.

**What it declines.** Functions, triggers, inserts, grants — counted, not
guessed at. A syntax error names the file. An empty file changes nothing.

**MySQL** is normalised into the same grammar rather than parsed by a second
one ([ADR-0004](adr/0004-mysql-is-normalised-into-the-one-grammar-and-says-what-it-dropped.md)):
backticks, `int(11)`, `ENGINE=InnoDB`, `KEY` clauses inside `CREATE TABLE`,
`MODIFY` and `CHANGE COLUMN`. A partition clause, a generated column, a
fulltext or spatial index, a trigger or a routine is **skipped and counted** —
a half-read `CREATE TABLE` is worse than a missing one.

## 2. A live PostgreSQL

`--database-url` or `LEDGERLINE_DATABASE_URL`. Everything comes from
`pg_catalog`; nothing is written and no row is touched. `pg` is an optional
peer dependency loaded only here, so a project that never uses this pays
nothing for it.

The output is the same shape as the migrations reader produces, in the same
canonical order, so the two can be compared byte for byte.

## 3. Prisma — `schema.prisma`

Read with `@mrleebo/prisma-ast`, which parses the grammar and nothing else —
no engine, no binary, no network. `@@map` renames a table and `@map` a column,
and `@relation(fields:, references:)` is the foreign key the migrations will
carry.

## 4. Rails — `db/schema.rb`

Generated by Rails *from the database*, so for a Rails team it is a faithful
statement of what is there — and it is checked in, which means Ledgerline can
read a repository whose migrations directory holds only Ruby.

Reads `create_table`, every `t.<type>`, `t.references`, `t.belongs_to`,
`t.timestamps`, `t.index … unique: true`, and `add_foreign_key`. Handles
`id: false`, `primary_key:`, `limit:`, `precision:`/`scale:`, `array: true`.

**The inflector.** `add_foreign_key "orders", "users"` names no column; Rails
derives `user_id` by singularising. The regular rules are here plus a list of
irregulars — and a *false finding* on Mastodon corrected it: a rule saying *a
word ending in `is` is already singular* is true of `analysis` and false of
`custom_emojis`.

## 5. Django — `models.py`, or a `models/` package

**The table name is `<app label>_<model lowercased>`, and the app label is the
app's directory.** A large project splits its models into a package —
`netbox/dcim/models/devices.py` — so the label is the directory *above*
`models/`. Getting that wrong renames every table in the schema.

Every field spans as many lines as it likes, because that is how real Django is
written. `ForeignKey('dcim.Cable')` reaches into another file, so every file is
read before anything is resolved.

Reads the field classes, `Meta`'s `db_table`, `unique_together`, `managed` and
`abstract`, `db_column`, and the three relation fields. A `ManyToManyField`
becomes the join table Django creates, because a diagram that omits it is
missing a table.

**What it declines.** A `GenericForeignKey` is reported, not drawn: it is a
polymorphic association — a real relationship, and not a foreign key.

## 6. SQLAlchemy

The friendliest of them, because it hides nothing: `__tablename__` is written
down, the column names are written down, and `ForeignKey('customers.id')`
names its target as a string. No convention has to be reproduced and no
inflector is involved — which is why its reader is the shortest of the seven.

Both spellings: the classic `Column(...)` and the 2.0 `mapped_column(...)`
with `Mapped[int]` annotations, where `Optional[...]` carries the nullability.

**What it declines.** `relationship()` is Python-side navigation, not a
column; the column it travels over is already read from its `ForeignKey`.

## 7. TypeORM

The decorators are the grammar: `@Entity`, `@Column`, `@PrimaryColumn`,
`@PrimaryGeneratedColumn`, `@CreateDateColumn`, `@ManyToOne`, `@OneToOne`,
`@JoinColumn`, `@Index`, `@Unique`. The table name is the class name in
snake_case unless `@Entity('x')` says otherwise, and a relation's column is
`<property>_id` unless `@JoinColumn({ name })` says otherwise.

Reading it as text matters more here than anywhere: an entity file imports the
rest of the application, so importing one runs a great deal of somebody else's
code.

## 8. sequelize-typescript

A Sequelize repository has **no file that is the schema**: its migrations are
JavaScript calling `queryInterface.createTable` and its models are decorated
classes. Outline is 30 MB of TypeScript with 56 real SQL statements in it and
was completely unreadable until this reader existed.

`@Table({ tableName })` names the table; a class no `@Table` decorates is a
base or a helper and not a table; and **a base class lends its columns to
everything that extends it** — which is where the primary key lives in every
Sequelize repository worth reading.

**The bug worth knowing about.** `class IdModel<T extends object = any>
extends Model<T>` contains two `extends`, and the first is a constraint on a
type parameter. Taking the first gave all 54 of Outline's models the base
class `object`, so every one lost its primary key — and a schema with no
primary keys still lays out, still renders, still looks like a schema.

## 9. Go structs — xorm and GORM

The last large ecosystem to get a reader, and the one this tool has most to
say about: **neither ORM creates a foreign key constraint**, so a Go
application of that shape keeps every relationship in its queries. Woodpecker
CI reads as 19 tables and 29 columns whose names promise a relationship that
nothing declares — every one true by construction.

`func (X) TableName() string { return "…" }` names the table when the
repository defines one, and it is often in a different file, so every file is
read first. Where there is none, the ORM's own default mapper is used —
xorm's is snake_case, GORM's is that pluralised — and **the assumption is
reported**.

Column names come from the quoted name in an xorm tag (`xorm:"INDEX
'user_id'"`), `column:` in a GORM tag, or the field in snake_case. A field
tagged `-` is not a column; a struct with no ORM tag anywhere is not a table.

## 10. EF Core — `…ModelSnapshot.cs`

C# generated by EF Core, and the one file in a .NET repository that states the
whole schema in one place. Its shape is why it reads cleanly: the file
declares an entity's properties, keys and indexes, and then a **second block
for the same entity** further down declares `HasOne(…).HasForeignKey(…)`. So
the reader collects entities first and resolves relationships after, exactly
as EF Core writes them.

`HasColumnType("integer")` is already the database's own spelling, which is
what [ADR-0002](adr/0002-a-schema-is-spelled-as-the-database-reports-it.md)
asks for, so those types are taken verbatim. `HasColumnName` renames, and the
rename follows the property into the key.

**What it declines.** `OwnsOne`, `OwnsMany`, `HasDiscriminator`,
`ComplexProperty` — shapes this reader does not flatten into tables, named
rather than approximated.

## The order they are tried

Migrations first when they yield anything, then Prisma, Rails, EF Core,
TypeORM, Sequelize, Go structs, and Django or SQLAlchemy last. **Never two at
once.** Two answers to one question is the thing this tool exists to complain
about, not to produce.

A migrations directory that exists and yields **no table** is skipped rather
than obeyed — Rails puts Ruby in `db/migrate`, so the directory matches the
search and contains nothing readable while `db/schema.rb` sits beside it.

## When none of them finds anything

`check` **fails**, and prints where it looked:

```
fail: No schema was found, so nothing was checked. This is a failure, not a
      pass — a check that reads nothing must not go green.
    looked for migrations in: db/migrate
    looked for an ORM schema in: db/schema.rb
    set "migrations" in ledgerline.json, or pass --database-url.
```

That used to print *No findings. Every relationship the queries rely on is
declared* and exit 0. In a pipeline it is the worst failure this tool can
have: move the migrations, and the build is green for ever after.
